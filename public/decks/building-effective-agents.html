The Agent Loop — A model in a loop with tools

The model isn't running the loop. Your code is. The model is a stateless function that turns one sequence of text into another.

The Agent Loop — The loop, in code

messages = [{"role": "user", "content": prompt}] for _ in range(max_iters): response = client.chat(messages, tools=tools) messages.append(response.message) if not response.tool_calls: break for call in response.tool_calls: result = dispatch(call) messages.append(tool_result(call.id, result))
Twelve lines here, about thirty with the tool definitions and setup. Everything else in this talk is a decision about some part of it.

The Agent Loop — What writing it yourself reveals

The model proposes, we execute. Every safety boundary lives in that gap.
"Done" is a decision we made, not something the model told us.
State lives in the message history — which is what makes it debuggable.
The loop took an afternoon. Everything around it took months.

Frameworks — We deleted ours

We ran real proof-of-concepts and picked LangGraph. Two finalists, both passed, no decisive reason between them.
During beta — before any production traffic — I hit a bug in its TypeScript tool-calling loop.
So I audited what it was still giving us. Observability: already ours. Routing: already ours.
The loop was the only thing left. I rewrote it, dropped the dependency, and the system got simpler.
The framework didn't change. Our infrastructure had. Which means "we evaluated this already" expires — re-run the audit.

Tools — Your user is the model

Tool design is interface design. Everything you know about UX still applies.
The model never sees your implementation. The MCP spec makes the contract explicit: it sees three fields.
Name is the button label. Description is the tooltip. Schema is the form. What you return is the screen after submit.
{ "name": "get_issue", "description": "Retrieve detailed information about an issue by ID, including attachments, git branch name, and active Triage Intelligence suggestions when the issue is in triage", "inputSchema": { "type": "object", "properties": { "id": { "type": "string", "description": "Issue ID or identifier (e.g., LIN-123)" }, "includeRelations": { "type": "boolean", "default": false, "description": "Include blocking/related relations" }, "includeReleases": { "type": "boolean", "default": false } }, "required": ["id"] } }

Tools — Overlap costs more than count

Read only your tool names and descriptions. Could you pick the right one? If not, the model can't either.
search_orders(query) find_orders(query)
list_issues(filters) → many get_issue(id) → one
Overlapping. Both plausible, so the model picks inconsistently.
Adjacent, but the boundary is obvious from the shape.
Some teams run fifteen or more distinct tools without trouble; others struggle with fewer than ten overlapping ones. Overlap is the expensive part, not the count.

Prompting — A prompt is a policy, not a request

What is my scope, and what is out of scope?
When am I done?
What do I do when I'm uncertain?
What am I never allowed to do?
These get answered at turn thirty whether you wrote them down or not. If you didn't, the model improvises an answer.

Prompting — One agent, four answers

A support triage agent: reads an incoming ticket, tags it, and either drafts a reply or escalates.
What's my scope?"You triage inbound support tickets. You do not issue refunds, change billing, or modify accounts."
When am I done?"Done means the ticket has a tag, a priority, and either a draft reply or an escalation note."
What if I'm uncertain?"If you can't tell the product area, search past tickets. If it's still unclear, tag it needs-human and stop."
What can I never do?"Never send a reply without a draft step. Never close a ticket."

Prompting — Finding the right altitude

Anthropic's word for how specific your instructions are. Fly too low and you see every rock but no route; too high and you see the country but no detail.
Too low — "if the ticket says refund, and the order is under 30 days, and it isn't flagged, then…" times twelve. The thirteenth case has no principle to fall back on.
Right — "Prefer resolving for the customer. Escalate anything you can't verify." Handles the case you never wrote down.
Too high — "Use good judgment." Whose judgment? It has never seen your refund policy.

Prompting — Two principles people skip

Say what to do when uncertain. An agent facing ambiguity will do something. If you didn't say what, it improvises.
"You must always call a tool" gets you null arguments and invented inputs — so any mandate needs an escape hatch: "if you don't have enough information, ask for what you need."
Don't say it in both places. The tool description owns how to call it. The prompt owns strategy across tools.
The failure I see constantly: incident, add a rule, repeat. Six months later the prompt is a bug tracker. Minimal doesn't mean short.

Evals — You can't eyeball this

An eval is a fixed set of your real tasks with known-good outcomes, scored the same way every time.
Reliability per turnA 13-step task completes correctly
90%25% of the time
93%39% of the time
95%51% of the time
Three points of per-turn reliability nearly doubles your completion rate.
Three points is invisible across five transcripts. It is very visible to someone running the agent a thousand times a day.
For scale: OpenAI reports close to +20% on their own internal SWE-bench Verified set from three added prompt sentences, about +4% from one of them, and about +2% from passing tool schemas through the API instead of the prompt text. A different benchmark from yours — but it tells you the size of effect you're hunting.

Takeaways — Three things to try

Audit your tool names and descriptions. Could you pick right from the names alone?
Write down what your agent should do when it's uncertain.
Turn your last production failure into one eval case. One input, one known-good outcome.
